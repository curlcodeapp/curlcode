# 0002: Data-model compatibility for the deferred routine execution/scheduling module

## Status

Accepted

## Context

SDS §31.1 explicitly defers routine execution, scheduling, adherence, and outcome feedback
(§20's `RoutineExecution` schema) past this MVP, but requires that "the data model must reserve
compatible identifiers and version references so the module can be added without redesigning
routines or evaluations." §34.2 additionally expects evaluation reproducibility via stable
version references (`profile_version_id`, `routine_version_id`, `product_version_ids`,
`rule_version`, `engine_version`).

Rather than add unused columns or an empty `routine_executions` table now — which would be
exactly the kind of speculative scaffolding this project has deliberately avoided everywhere
else (see `CLAUDE.md`'s "what not to do") — this ADR is a compatibility review: does today's
schema (`routines`, `routine_steps`, `routine_step_products`, `overrides`, from the M2/M4
migrations) block a future `routine_executions` table, or can one be added cleanly later?

## Decision

**Compatible today, no changes needed:**

- Every entity (`routines`, `routine_steps`, `routine_step_products`, `overrides`) uses a `uuid`
  primary key, generated by `gen_random_uuid()`. A future `routine_executions` row can reference
  `routine_id` (and `routine_step_id` for per-step completion/skip tracking) via ordinary foreign
  keys without any migration to the referenced tables.
- `routines.wash_cycle_days` already exists as a plain scalar. A future
  `routine_executions.wash_cycle_number` naturally derives from counting execution rows per
  routine — no schema change to `routines` required to support it.
- `routines` rows are, in practice, immutable after creation today — `activateRoutineTemplate`
  only inserts, nothing currently updates a routine or its steps in place. This means today's
  rows already behave like the "immutable RoutineVersion snapshot" §34.1 calls for, even without
  a formal versioning table. A real `RoutineVersion` snapshot table is only needed once routine
  _editing_ is added — that's a separate future decision, not blocked by anything here.
- RLS on all four tables is join-based back to `routines.user_id = auth.uid()` (see
  `supabase/migrations/20260726000000_hair_profiles_routines.sql` and
  `20260726000002_overrides.sql`). A `routine_executions` table can reuse the identical policy
  pattern.

**One real gap, to resolve when this module is actually built, not now:** every foreign key in
today's schema is `on delete cascade` (deleting a routine deletes its steps, product
assignments, and overrides). There is currently no UI or action that deletes a routine, so this
is inert today. But it would directly violate SDS's "raw facts are immutable" principle (§3) once
execution history exists — a user deleting a routine shouldn't erase the historical record of
washes completed under it. When routine deletion and execution history are both built, routine
deletion must become a soft-delete/archive (matching the existing `status: 'archived'` value
already defined on `routines.status`) rather than a hard delete, or `routine_executions` needs
`on delete restrict`/`set null` instead of cascade.

## Consequences

- No migration or schema change needed for M5. This ADR is the artifact that satisfies SDS
  §31.1's "reserve compatible identifiers" requirement — a documented compatibility analysis,
  not speculative unused code.
- The one identified gap (cascade delete) is not urgent to fix now (nothing deletes a routine
  today), but must be addressed _before_ shipping both routine deletion and execution history in
  the same future milestone — noted here so it isn't rediscovered from scratch later.
